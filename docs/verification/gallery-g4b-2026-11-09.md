# G4b: similar-photos retention guard at the choke point and the REVIEW action bridge

Date: 2026-11-09. Base: `a057a3e` (work branch with G1a, G1b, G2 tooling and the G4a read-only comparison). Branch `g4b-guard`, local, not yet a PR. Decisions C227–C234 in [progress](../progress.md). This increment is destructive code: it lets explicitly chosen REVIEW photos of a similar-photos group reach the existing review-trash path, behind a new typed keep-one guard at the choke point. No model, no network, no new dependency.

## What was built

- **Typed retention evidence (C227, GAL-8, AC-G6).** `core:safety` gains `VisualRetention(groupId, groupVersion, retained: List<RetainedMember(ref, path, size, mtime, identity)>)` and `PlannedOp.visualGroups` (empty for every existing op; nothing existing changes meaning). `SafetyGuard.check` refuses the whole plan when the evidence is misplaced (anything but a plain REVIEW `TRASH` of one file with no duplicate group, witness, SHA-256, backup proof, verified copy or "last copy"), malformed (blank ids, a group named twice on one op, different evidence for one group, a kept MediaStore row without an identity), keeps nothing, or keeps a member that any op of the same plan acts on (by ref and by canonical path: choosing every member, overlapping groups, another spelling). `ActionExecutor` re-reads every kept member right before each op of the group, after the existing re-checks and the handler's veto and also in test mode; any kept member that is missing, unreadable, a link or folder, changed in size, time or identity, PROTECTED now or kept now refuses the group for the rest of the run (`SkipReason.RETAINED_MEMBER_GONE`, reported, never deleted). `FreeOriginals` maps the new reason to "other".
- **Never equality, never permanent (C228, GAL-3).** `PermanentKinds.reasonFor` and `verifiedBackupReason` return null for an op with similar-photos evidence; such an op is always handed over as `TRASH`.
- **Choices (C230, GAL-4/6/8/9).** In the comparison, REVIEW photos are checkboxes, none chosen at first; memories (MOVE) stay buttons that open the photo, with "Back up" only. `GalleryController` keeps choices in memory per group id and group-version digest; it offers a photo only while every group it belongs to (from the comparison's full grouping, also overlapping or hidden groups) keeps another available unchosen photo. Every scan re-syncs the shown members: a photo the latest scan no longer has with the compared size and time leaves its groups and its choice. Nothing is saved; the confirmation's open state is plain `remember`.
- **Bridge (C231, GAL-7).** `GalleryReview.plan` builds `CleanPlanner`'s plan for the chosen photos (REVIEW, `TRASH`, no exact-duplicate evidence), attaches the evidence of every group each photo belongs to (kept = the group's available unchosen photos) and sets each MediaStore photo's expected identity from the generation the comparison read. "Delete …" (exact count and size) opens the existing `EditableConfirm` ("Move to trash", ✕ per photo, Cancel); the user's tap names exactly the shown photos. `HomeViewModel.cleanGallery` runs the plan through the existing clean path: the comparison pauses, test mode simulates, the executor re-checks, MediaStore rows go to Android's dialog, history records only what happened.
- **Recovery and accounting (C232, C233, GAL-21).** For a gallery result, Undo asks Android to put back exactly the rows it trashed (`MediaConsent.undoable`, `CleanResult.androidTrashed`); a restore result says "… restored from the gallery's bin." Results count what went to a trash, never "freed"; a refused group has its own line. Choosing changes no lane total.
- **Architecture (C231).** `ArchitectureTest` "the gallery review bridge is narrow and the only maker of similar-photos evidence". `Gallery.kt` and `GalleryScreens.kt` still import no safety type and name no plan or confirmation.
- **Strings.** New: `gallery_compare_hint_choose`, `gallery_review_choose`, `gallery_skipped_kept_changed` (plural), `android_trash_restored`; removed: `gallery_review_later`. English and Hebrew; Help's "Similar photos" topic updated.

## Not verified

- No phone run. Owner checks G4b-1 (test mode), G4b-2 and G4b-3 (at home, disposable copies) in [progress](../progress.md) map gallery checklist items 4, 5 and 8.
- `GalleryReviewOnDeviceTest` was compiled locally (`:app:compileFossDebugAndroidTestKotlin`); it runs on the API 30/36 emulators in CI (pending CI). It uses rows the test inserted itself; Android's dialog for other apps' photos can't be answered by a test.
- Android's own dialog runs after the executor's checks; a kept photo that another app removes while that dialog is open is not seen (as for every existing MediaStore deletion).
- The guard's protection is relative to the groups the app names. The comparison's grouping quality (thresholds, keeper reasons) is the uncalibrated G1a/G1b policy; no photographic accuracy, speed or battery result is claimed.
- Choices are not persisted (GAL-9's deferred decisions after process death remain G4a-2). No swipe review of a group.
- Items from the foss all-files walk are still not compared (no guarded reader), so groups hold MediaStore rows only and always use Android's trash, not KeepClear's folder trash.
